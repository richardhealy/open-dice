# Dice runtime performance (roadmap D1-D4)

Date: 2026-10-20. Branch `claude2/perf-dice-runtime`. Scope set by the owner: D1-D4 only, all
**non-visual** (the dice must look and move exactly as today); D5 (shadows) is not touched;
no npm publish and no RollQuest bump until the owner has reviewed renders and a roll video.

## How a roll is decided today (read before changing anything)

- `roll()` / `addDice()` call `_preSimulateInLiveWorld`: hidden prediction dice are thrown
  into the live `this.world` with random seeds and stepped synchronously (`world.step(1/60)`,
  at least 60 and at most 5,000 steps) until every new die rests. The face that lands up is
  read with `getDieValue`, the prediction bodies are removed and existing dice are restored.
- `_spawnBatch` then creates the visible dice with the **same seeds**, paints the target value
  onto the predicted landing face (`closestIndex`) and the animation loop simulates the throw
  a second time in real time (`world.step(1/60, dt, 2)`). Same world, same seeds, same
  integrator, so the second run retraces the first and the painted face lands up.
- Results are therefore **forced**: a die with `rolled` always shows `rolled`; a die without
  `rolled` reports the face that physically lands. Spectators receive the values and roll
  with `rolled`, using their own random seeds. No client re-simulates another client's
  throw, so cross-client physics determinism is not required. The physics config is not
  changed by this work anyway, so old and new package versions can share a game.
- Quirk to preserve: walls use a `Material('wall')` instance that is not the one in the
  dice-wall `ContactMaterial`, so dice-wall contacts use cannon's default contact material.
  Anything that rebuilds the world must keep that.

## D1. The roll freeze

The freeze is the synchronous prediction. The second simulation runs at 60 Hz in the
animation loop and costs CPU every frame.

Not done: lowering `SOLVER_ITERATIONS` or switching to `SAPBroadphase`. Both change the
simulation (Gauss-Seidel results depend on iteration count and equation order, and SAP
orders pairs differently), so the same throw would bounce and settle differently. That is a
visible change, which the owner ruled out.

Done instead (the roadmap's "better" and "best"):

1. `src/physics-sim.js` (cannon-es only, no three, no DOM): `describeWorld` turns the live
   world plus the dice to simulate into plain data (bodies in world order, shapes, materials
   by identity, contact materials, solver settings, rest counters); `buildWorld` rebuilds an
   identical world; `simulateThrow` steps it with exactly the old loop (min 60, max 5,000,
   stop when every new die rests) and records, after every step, each moving body's position,
   quaternion, velocity, angular velocity and rest counter, plus every `collide` event with
   its impact speed.
2. `src/physics-worker.js` runs `simulateThrow` in a Web Worker (bundled inline, so the
   package needs no extra file). `src/prediction.js` sends requests to one shared worker and
   falls back to running the same function synchronously on the main thread when Workers
   are unavailable, fail to start (CSP) or error.
3. The roller replays the recording instead of simulating twice: during a replay the replayed
   bodies are out of the live world; on each internal physics step (`postStep`, so the
   60 Hz pacing, the two-substep cap and frame timing stay as they are) the next recorded
   state is written into each body and its recorded collisions play their sounds. When the
   recording ends, the bodies go back into the world in their original order and the live
   world takes over from the identical state (normally the dice are at rest by then).
4. While a prediction is in flight the live world does not step (today the whole page is
   frozen for that time), rendering and effects keep running, `isRolling()` is true, and
   predictions are serialized so concurrent `addDice` calls see each other's dice. A `roll()`
   made while an earlier one is still predicting supersedes it (the earlier promise stays
   pending, as a wiped batch's always has). `addDice` re-predicts if a `roll()` changed the
   table while it was waiting.

Proof: a unit test runs today's two simulations (the live-world prediction and the
re-simulation of the visible dice) and the new recorded path for hundreds of seeded throws
covering every die type, d100 pairs, model dice and `addDice` with dice already on the table,
and requires the pose sequences to be bit-identical, step by step. A second test checks the
worker path and the synchronous fallback give the same recording.

## D2. GPU leak and first-frame stutter

- Classic face textures go through a reference-counted cache keyed by everything that
  changes their pixels (text or d4 corner values, colours, decal, secret, offset, texture
  flags). Dice with the same look share textures, so a repeated roll paints and uploads
  nothing. Released textures are disposed only after the next batch has been built (so the
  next roll reuses them), and never while any die holds them. This keeps the earlier review
  concern (no texture pinned for every colour pair ever rolled) satisfied.
- One geometry per classic die type, shared by every die and prediction body of that type,
  never disposed.
- When dice leave (`roll()`, `reset()` after its fade, `destroy()`), each die's own materials
  are disposed (classic, design and model-die materials, labels, liquid). Shared things are
  never disposed: the placeholder material, set/label textures in the texture cache, model
  template geometries and textures, shared classic geometries.
- Test: unit tests on disposal ownership; a browser run checks `renderer.info.memory` stays
  flat over many rolls and after a design change, and screenshots stay identical.

## D3. Sounds

`SoundManager` fetches and decodes each sound once into an `AudioBuffer` and plays it through
a `GainNode` set to the same linear volume (`volume * impact`) the `<audio>` element used.
Random pick, overlap and the impact mapping in the roller are unchanged. It resumes the
`AudioContext` on the first user gesture and on play; while the context is not running, or
when Web Audio, fetch or decoding is unavailable for a sound, it plays that sound exactly as
today (a cloned `<audio>` element), so blocked or muted audio behaves as before.

## D4. First roll in a painted design

`preloadSets(ids)` paints one die type at a time and yields to the browser between them
(`requestIdleCallback`, else `setTimeout`), so calling it at idle time never makes a long
task. It only loads the designs it is given. RollQuest change (not in this PR): call
`preloadSets` for the table's painted designs at idle time, as it already does for model
designs.
